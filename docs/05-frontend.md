# 05 · Frontend

Stack: **Next.js 16 (App Router, Turbopack) · React 19 · TypeScript · wagmi 3 · viem 2 · Tailwind 4 · @tanstack/react-query 5**. Package manager: npm.
There's no backend in v1. Every read and write goes straight to Monad over RPC.

Status: Phase 2, in progress. `✓` = built, `…` = still to do.

### Config

- `next.config.ts` loads the **repo-root `.env`**, so the web app and the Foundry scripts share one file. `web/.env*` still overrides it.
- Every value has a default pointing at the Phase 1 testnet deployment, so `npm run dev` works with no `.env` at all.
- `NEXT_PUBLIC_CHOG_MINTABLE=false` hides the mint panel; set it for the real collection.
- With `NEXT_PUBLIC_PRIVY_APP_ID` set, **Sign in** opens Privy (email, Google, X, Discord or a wallet), embedded wallets are created for people without one, and `/account` links and unlinks accounts ([ADR 0010](adr/0010-privy-sign-in.md)). Without it, only injected wallets (MetaMask, Rabby, Phantom, Backpack and anything else announcing via EIP-6963). WalletConnect in wagmi 3 needs `@walletconnect/ethereum-provider` and a project id, so it was left out of v1.

### Design tokens

The UI follows a two-layer token architecture: Chog brand primitives live as `--chog-*`
variables, while components consume semantic roles such as `--surface-raised`,
`--content-primary`, `--action-primary`, and `--feedback-warning`. Border radii and shadows
are also centralized as component-ready tokens. This keeps the brand palette changeable without
scattering hex values through JSX or utility definitions.

### ABIs

`@wagmi/cli` with the Foundry plugin reads `contracts/out/{OnDeal,MockChog}.sol` and writes `lib/abi.ts` (`onDealAbi`, `mockChogAbi`, both `as const`). It isn't generating hooks. The generic wagmi hooks are fully typed from the `as const` ABIs, which is enough. The file is committed so the app builds without Foundry; run `npm run abi` after changing a contract.

### Copy vocabulary

The app isn't limited to Chogs (V2 handles any ERC-721, ERC-20 and MON), so UI text says **asset** for anything in a deal, **NFT** only where it must mean an ERC-721, and **MON** for the native coin. "Chog" appears only where it is the actual thing on screen: Chog artwork, the Chog picker and trait names, and the MockChog mint panel. Error copy in `lib/errors.ts` follows the same rule.

### Open Deals search

Client-side over the loaded deals (up to 200 while a filter is active). A bare number matches the deal id or a Chog id on either side; other text matches the maker/taker address or a trait, as `Hat: Crown` or just `crown`. Traits come from one `traitsOf` multicall over the Chog ids in view. A trait request only stores a Merkle root on-chain, so the page also reads the catalog (`totalSupply` + `traitsOf`) and names the request by finding the trait whose set hashes to that root. That only resolves while the matching set is unchanged, the same condition the fill flow needs. The search box offers the trait labels in view as suggestions.

### Open Deals tabs

- **Open**: status Open, not expired, and either public or addressed to me.
- **For you**: open direct offers where `taker = me`.
- **All**: everything loaded, any status.

### Notifications

A bell in the header (connected wallets only). There is no event stream to subscribe to ([ADR 0003](adr/0003-no-indexer-in-v1.md)), so `lib/notifications.ts` derives every notification from the deals `useDeals` already loads (up to 200, polled every 8s):

| Kind | When |
|---|---|
| For you | an open direct offer with `taker = me` |
| Accepted | a deal I made is Filled |
| Ending soon | my open deal expires within 1h |
| Expired | my open deal ran out and its escrow is still locked |

Read state is a set of `kind:dealId` keys in localStorage, per wallet. On the first visit of a wallet, existing Accepted items are marked read so old deals don't show up as news. Direct offers and expiries stay unread because they need action. The optional browser alert (`Notification` API, turned on from the bell's panel) fires for items that turn up while the tab is in the background. It can't reach a closed tab; that needs a server-side trigger.

### OnDealV2 in the frontend (Phase 4)

V2 ([ADR 0005](adr/0005-generic-asset-model.md)) is optional: nothing changes until `NEXT_PUBLIC_ON_DEAL_V2_ADDRESS` is set, and `swapV2` in `lib/contracts.ts` is `undefined` before that.

**Reused as is:** wallet, header, providers, `useTxFlow`, `TxButton`, `errors.ts` (V2 error copy added), `format.ts`, `useNow`, the Chog art and thumbnails, `useChogs`, and the notifications and deal-filter logic.

**New, V2-specific:**

| File | Purpose |
|---|---|
| `lib/assets.ts` | `Asset` (native / ERC-20 / ERC-721), `formatAsset`, `sameAsset` (the contract's duplicate rule) |
| `lib/dealsV2.ts` | `DealV2` (two `Asset[]`), `toDealV2`, and `toLegacyDeal` |
| `hooks/useDealsV2.ts` | `tradeCount` + multicall `getTrade`, like `useDeals` |

`toLegacyDeal` converts a V2 deal to the v1 `Deal` when it only holds Chogs and MON, so the existing cards, filters and notifications show those deals with no change. A deal that includes any other token returns `null` and needs the generic asset UI below.

**Screens** (hidden until V2 is configured):

| Route / file | Purpose |
|---|---|

| `/v2/deal/[id]` | Both sides as `AssetList`, then cancel / reclaim / accept, and a "collect" panel for held payouts. An open offer shows the note and the offers instead of an ask (see below) |

| `hooks/useAssetApprovals.ts` | The approvals still missing, one step at a time |
| `hooks/useDealV2.ts` | One deal by id, plus its note (`getTrade` + `offerNote` in one multicall) |
| `hooks/useProposalsV2.ts` | The newest offers on an open offer: `proposalCount` then one `getProposals` page, newest first, with `loadMore` |

Choices worth knowing:

- **Approvals are exact for tokens, collection-wide for NFTs.** An ERC-20 is approved for the amount in the deal, no more. An NFT collection uses `setApprovalForAll`, the only way to cover several ids in one transaction. The button shows the next missing approval ("1 of 3"), then turns into Create / Accept.
- **Token names come from the token.** The editor shows the symbol and decimals read on-chain under each address, and amounts are parsed with those decimals. A row with more decimals than the token has is rejected instead of rounded.
- **Held payouts:** the deal page reads `claimable` for every asset in the deal and offers a Claim button for what the connected wallet is owed.
- **Lists:** Deals and History show a **Chogs / Multi-asset** switch (only when V2 is configured). Each version has its own book: `/deals` renders `DealsV1` or `DealsV2`, and History reads whichever `useDeals` / `useDealsV2` matches. The switch is page state, not a URL param, and it defaults to Chogs.
- **V2 cards:** `DealCardV2` reuses `DealCardFrame` (the chrome `DealCard` also uses) and fills the two sides with `AssetSide`: Chog art for the Chog collection, a plain tile for any other NFT, a token tile with the on-chain symbol, and the MON pill.
- **V2 search:** `lib/dealFiltersV2.ts` matches deal id, NFT id, maker / taker, token address and on-chain symbol, with the same MON filter and sort as v1. V2 search doesn't look inside trait requests yet: their traits are in the deal's spec, which only the deal page reads.
- **Fills are per contract:** `useLocalFills(account, contract)` keys the record by swap contract, so a v1 deal #3 and a V2 deal #3 don't collide. The V2 detail page records a fill after Accept confirms.
- **Open offers ([ADR 0007](adr/0007-open-offers.md)):** a deal with an empty ask (`isOpenOffer`). The card's "wants" side reads *Open to offers*. On the detail page the right-hand panel shows the maker's note as plain text (never linked or rendered as markup) with a "not verified" line, and below the actions come the offers, newest first. The maker sees **Accept & swap** and **Reject** on each active one; whoever made an offer sees **Withdraw my offer** while it is active, even after the deal settled or was cancelled. Anyone else who is allowed to (not the maker, and the private-offer wallet if one is set) gets the **Send offer** form: an `AssetEditor` whose assets are locked in escrow, with the same one-at-a-time approvals. Closed offers sit in a collapsed list. The Accept button and the direct `fillTrade` path are never shown together: `canFill` is false for an open offer.
- **Offers and History:** a wallet whose offer was accepted is the taker, but nothing on the deal says so without reading the offers. The detail page records it like a fill (`useLocalFills`) when it sees an accepted offer from the connected wallet, so History picks it up after that visit.
- **Held payouts on open offers:** `claimable` is read for the deal's assets, the accepted offer's assets, and the connected wallet's own offers, not for every offer on the deal.
- **Not built yet:** V2 in the notifications bell (so no "you got an offer" alert yet), offer counts on the list cards, the offer note in list search, and the `?v=` deep link.

### Choosing NFTs (NFT picker)

An NFT row is no longer a collection address plus a typed id. **+ NFT** (and **Change** on a row) opens `components/NftPicker.tsx`:

1. **Collection.** A search box over the collections the app can know about without an indexer: the Chog collection and `NEXT_PUBLIC_KNOWN_COLLECTIONS` (*Featured*), the ones this browser used before (*Recent*, localStorage), and the ones open deals and signed swaps use (*In open deals*, from `useMarketCollections`). Search matches name, symbol or address. **Pasting a contract address** reads it on-chain first (`supportsInterface` for ERC-721, then name, symbol, supply) and refuses anything that isn't an NFT collection.
2. **Tokens.** On the side the wallet is giving (the editor gets `owner`), the wallet's own NFTs in a grid with art, via `tokenOfOwnerByIndex` (first 100). On the side it is asking for, the collection is browsed a page at a time via `tokenByIndex`, with the holder under each token. Tick several and add them in one go.
3. **Typed id.** Below the grid, for collections that can't list tokens or ids the grid doesn't show. The id is checked with `ownerOf`: it must exist, and on the giving side must be the wallet's.

| File | Purpose |
|---|---|
| `lib/collections.ts` | The read ABI, featured and recent collections, `safeImage` |
| `hooks/useCollection.ts` | `useCollectionInfos`, `useOwnedTokenIds`, `useBrowseTokenIds`, `useTokenViews` (art and name from `tokenURI`), `useTokenOwner` |
| `hooks/useMarketCollections.ts` | Collections used by open deals and signed swaps, most used first |
| `components/NftPicker.tsx` | The dialog |

Choices worth knowing:

- **No indexer, so no "all collections" and no "everything I own".** A collection that isn't enumerable can't list a wallet's tokens, so the picker falls back to the typed, checked id. Finding a collection you hold means pasting its address, unless it's featured, recent or already in a deal.
- **Names are the contract's own words.** Any contract can call itself "Chog", so every collection is shown with its short address, and only the configured ones are tagged *Featured*.
- **Token art is an image URL from metadata**, so only `http(s)` and inline `data:image/` are shown (`safeImage`), in a plain `<img>` with no referrer.
- Draft rows are unchanged (`token`, `value`), so `assetDraft`, approvals and the contracts see nothing new. Not done: the same search for ERC-20 tokens (a pasted address still shows its on-chain symbol and decimals).

### Intents in the frontend (Phase 4)

Signed intents ([ADR 0008](adr/0008-trade-intents.md), [0009](adr/0009-ring-swaps.md)) are optional: the screens appear once `NEXT_PUBLIC_ON_DEAL_INTENTS_ADDRESS` is set, and `swapIntents` in `lib/contracts.ts` is `undefined` before that. They are not a separate product in the UI: a signed swap is a **deal that settles differently**, so it shares the Create wizard, the deals list and History with locked deals. They read and write the matcher's pool over HTTP (`NEXT_PUBLIC_POOL_URL`, default `http://127.0.0.1:8787`), so the matcher has to be running ([matcher/README.md](../matcher/README.md)). A pool that is down only costs the signed swaps (a notice in the list, an error on the sign step); locked deals read straight from the chain.

| Where | What |
|---|---|
| `/create` | Step 1 opens with **How should it settle?**: *Lock assets now* (the three deal kinds, as before) or *Sign only*. Sign only runs `SignedFlow`: want (no MON), give plus a deadline (default 1 hour), then review, the consent notice, **approve** and **Sign and post**. Both steps link back to *Lock assets* for a deal that needs MON or a trait request |
| `/deals` (Multi-asset) | Locked deals and open signed swaps in one grid, each tagged **Locked** or **Signed**. A *Type* filter (All / Locked / Signed) sits beside the MON and sort filters. Search, MON and sort apply to both. The page opens on Multi-asset once V2 and intents are both configured |
| `/history` (Multi-asset) | The wallet's signed swaps in every status beside its locked deals, with the same Active / Completed / Expired filters |
| `/guide#settlement` | *Locked deals vs signed swaps*: a comparison table and one anchored entry per chip (`#cant-fail`, `#costs-gas`, `#assets-locked`, `#free`, `#nothing-locked`, `#can-fail`), plus three FAQ entries. Shown only when intents are enabled. The sign review's consent notice links here too |
| `/intent/[hash]` | One signed swap: status and what it means, both sides, and for a settled one the cycle and what the maker received. The maker also gets approve-again (when paused), **Remove from pool** and **Cancel on-chain** |
| `/intents`, `/intents/new` | Redirect to `/deals` and `/create`, for old links |

| File | Purpose |
|---|---|
| `lib/intents.ts` | The EIP-712 types and domain, the struct hash (the intent's id), the pool's JSON shapes and their parsers, status copy, deadline presets, `nonceBit`, and `intentAsListing` (a signed swap shaped like a V2 deal, so the list and filters treat both alike) |
| `lib/pool.ts` | The HTTP client. Pool rejections become readable copy; rows whose recomputed hash doesn't match are dropped |
| `hooks/usePool.ts` | `usePoolInfo` (also flags a pool for another chain or contract), `useIntents`, `useIntent`, `useSettlements` |
| `hooks/useIntentReadiness.ts` | What stands between a wallet and an intent that can settle: balance and ownership problems, and the approvals still missing |
| `hooks/useSignFlow.ts` | Sign and post an intent, or sign a cancel. Free, no gas; reuses `TxState` with an added `posting` stage so `TxButton` works unchanged |
| `components/create/SettlementPicker.tsx` | The *Lock assets now* / *Sign only* choice: two cards, each with three chips (plus or minus) that open a tooltip |
| `components/Tooltip.tsx` | The one tooltip: opens on hover, focus or tap; closes on Escape, outside tap or blur; an optional "Learn more" link; shifts to the right edge near the screen edge. Its trigger is a button, so it can't sit inside another button or link |
| `lib/settlementTerms.ts` | The six chip terms: `id` (the Guide anchor), label, plus or minus, a tooltip `tip` and the Guide's longer `detail`. One source for the chips, the tooltips and `/guide`, so they can't drift apart |
| `components/create/SignedFlow.tsx` | Steps 1 to 3 of a signed swap |
| `components/IntentParts.tsx` | Status badge, `IntentCard`, `ListingGrid` (deals and signed swaps in one grid), `CycleView`, and `ConsentNotice` |

Choices worth knowing:

- **Approvals are the narrowest that work.** An ERC-20 is approved for exactly the amount given, an NFT with `approve(id)`. A checkbox switches to `setApprovalForAll` per collection for fewer transactions, with the wider permission spelled out. Approving is what lets a signed intent execute later without another confirmation, so the consent notice says it.
- **The deadline is short by default** (10 minutes to 7 days, default 1 hour) because a signature that has left the pool can't be recalled.
- **Nonces** are chosen at signing time: above everything this wallet has posted to the pool (cancelled intents included, since their signatures could still settle), skipping any the contract marks used. Keeping them in one 256-bit word keeps settlement cheap.
- **Two kinds of cancel.** *Remove from pool* is a signed `CancelIntent` message, free, but only this pool forgets it. *Cancel on-chain* sends `invalidateNonces`, costs gas, and is the only way to be certain. The detail page says which is which.
- **Paused intents** (the pool's `stale`) show why in plain words and, for the maker, the approval to fix it. The matcher revives it on its next 30s pass.
- **Matched in a ring.** `CycleView` lists each wallet's whole `give` and who got it. A pair reads "Swap", three or four wallets "Ring of N". The maker's detail page also shows what they received, surplus included.
- **Notifications.** The bell also lists the wallet's intents: settled, paused (needs action) and dropped, derived from the pool like the deal ones. Settled and dropped ones from before a wallet's first visit are marked read.
- **Ordering in the merged list:** deals have an id but no timestamp, and a signed swap has a timestamp but no id, so there is no honest "newest" across both. Signed swaps come first; *Ending soon* sorts the two together by expiry or deadline.
- **Not built:** counterparty restriction and trait wants (the contract has neither), a wallet NFT picker in the sign flow (ids are typed, as on the V2 create screen), per-token info beyond symbol and decimals, and push alerts while no tab is open.

### Deal Detail: which button shows

```text
status == Filled / Cancelled                → read-only badge
status == Open && expired                   → [ Reclaim to maker ] (anyone)   + [ Cancel ] if maker
status == Open && me == maker               → [ Cancel deal ]
status == Open && (taker == 0 || me == taker)
      && I own all requestedIds             → [ Approve ] → [ Accept & Swap ]
otherwise                                   → "You don't own the requested Chogs"
```

The **Escrow panel** keeps the spec's picture: `Maker ✓ deposited` (always true while Open) and `Taker ✗, pays on accept`.

## Clubs

[Spec](09-clubs.md), [ADR 0016](adr/0016-clubs-and-momentum.md). Two routes, `/clubs` and `/clubs/[address]`, with "Clubs" in the header's `NAV`. Nothing on these screens calls a contract: Clubs read the deals that `useDealsV2` and the pool already load, plus the Club routes under `/api/clubs`.

| Screen | Reads | Writes |
|---|---|---|
| **Clubs** `/clubs` | the verified list (`web/data/assets.json`) at once; `/api/clubs` fills in Momentum and counts; `/api/me/clubs` for "Your Clubs" | — |
| **Home** `/` (`#clubs`) | `ClubsIntro`: what Clubs are and how Momentum works; `ClubsTeaser` reads `/api/clubs` for the three busiest | — |
| **Club** `/clubs/[address]` | `/api/clubs/[token]`, the Market from `useClubMarket` (newest 200 deals + the pool's `token=` filter), `/members`, `/posts`, `/membership`, `/profile` | join/leave, post, report, and the staff actions below |

**Without a store or Privy,** the routes return `{enabled:false}` and the screens show a read-only Club with a "not configured" note (like `NotConfigured` on the Account page). The cards still draw from the list; only the numbers are missing, and a note says so.

**Explaining vs. using.** The home page explains Clubs (`components/ClubsIntro.tsx`: the three parts of a Club, the Momentum rules, the heat scale) and `/clubs` only works with them. `/clubs` is built for many Clubs: totals as chips, "Your Clubs", **Most active right now** (the top three by Momentum, as cards), **Rising this week** (biggest weekly gain) and **Most traded · 7 days** boards, then **All Clubs**: search by name, symbol or address, Collections / Memecoins, six sorts (busiest, rising, most traded, most members, recently active, A–Z), a list view (`ClubRow`, the default) or cards, remembered per browser, and "Show more" by 12. Archived Clubs sort last.

**Mock Clubs.** Outside production, `lib/demoClubs.ts` adds mock assets to `registry`: 11 Clubs at every pace (hot, busy, rising, steady, fading, quiet, one archived), two memecoins that share a collection's Club (CHOG with Mock Chog, TOADZ with Testnet Toads), and wrapped MON and a stablecoin, verified with no Club. The dev server's in-memory store is seeded with members, verified handles, posts, roles, swaps and a moderation log for every Club (`lib/server/demoClubs.ts`), through the same keys the real writes use. `NEXT_PUBLIC_DEMO_CLUBS=false` turns both off; the tests do. The seed runs once per server start.

**Look.** Each Club wears one of five brand covers (`.club-theme-N` in `globals.css`), picked from its address by `clubTheme()` in `components/ClubArt.tsx`, so it looks the same everywhere. `ClubAvatar` shows the asset's `image` from the assets list, or its initials on the cover colours; a collection is a rounded square, a token a coin. Cards and panels use `.club-card` / `.club-panel` (the cream sticker of `page-section` without the tape). `HeatMeter` puts Momentum into words with five bars: Quiet, Stirring, Active, Busy, Hot (`heat()` in `lib/clubs.ts`). The Club styles sit in `@layer components`, so a utility on the same element wins.

**Tabs:** Market, Board, Members, and Manage for staff only, each with its count, in the sticker tab bar. Which one is open lives in the URL (`?tab=board`), so a section can be linked; Manage needs the `role` returned by `GET .../membership`. Inside a section, second-level switches (For trade / Wanted / Recent swaps, the Board filter, the Members sort) use the lighter `components/Pills.tsx`. Per-row actions (report, delete, hide, pin, ban, roles, leave) sit behind a "⋯" `components/ActionMenu.tsx`, which asks `window.confirm` for what can't be undone.

- **Market** (`ClubMarket.tsx`): For trade and Wanted use `ListingGrid`; Recent swaps is the Club's latest completed swaps, with both sides. The page loads `useClubMarket` once and passes it down, so the tab count and the tab agree. An empty list says what would be there and offers Create deal. It says when the 200-deal scan limit was hit or the pool didn't answer.
- **Board** (`ClubBoard.tsx`, `PostItem.tsx`): a composer for members (Note or Looking for, a ring counting down the 280 characters, the link field) and the feed, pinned first, with an All / Looking for filter. A visitor sees a "Join the conversation" panel; a member who doesn't hold the asset in a holders-only Club is told why they can't post. Each post's menu offers Report, Delete (author or staff), and for staff Hide or Restore and Ban author, and for the Owner Pin. A hidden post shows "hidden after reports" to everyone else.
- **Members** (`ClubMembers.tsx`): the leaderboard, with a podium for the top three once three members have traded, a bar for each member's share of the top score, a Newest sort, `HolderBadge`, and Owner/Moderator chips. Staff get a menu by role: make or remove moderator, hand over, ban. It is shown only when the viewer's role may act on that row (`mayActOn` in `lib/clubRoles.ts`, the same rule the server applies), and the server decides regardless.
- **Manage** (`ClubManage.tsx`): the page editor (description, up to 3 `https://` links, "holders only can post"), the ban list, the "ownership changed on-chain" note (admins) and the moderation log as a timeline.

**Side column** (`ClubSidebar.tsx`): the heat scale with this Club's step marked, the top five traders (hidden while the Members tab is open) and the asset's details: contract with copy and explorer link, kind, and why it is verified. Below `lg` it follows the tab content.

**Header** (`app/clubs/[address]/page.tsx`): the cover with the avatar over its edge, name, symbol and kind, a Verified chip (its tooltip is the list's note), when it was last active, `JoinClubButton` (Leave sits in its "⋯" menu), the description and links, and a stats strip (Momentum and its weekly change, members and holders, swaps and new deals in 7 days, traders in 30 days, heat). Under it, as alerts: a **Claim** prompt for a member whose wallet is the token's `owner()` when the Club has no Owner, the archived note, and the activity-log note.

**Sign-in and writes.** `hooks/useSignIn.ts` opens Privy; `hooks/useClubMembership.ts`, `useClubBoard.ts` (`useClubPosts`, `useClubPage`, `useClubActions`, `useClubStaff`) use React Query and `useAccessToken`, send the Privy access token, and report errors through `useToast`. A failed load uses `LoadError`. Server refusals (`banned`, `cooldown`, `rate_limited`, `link_mismatch`, …) arrive as `{error, message}` and the message is what the toast shows.

**Rules the UI relies on:** posts are rendered as plain text (React escapes them, nothing is linked); the Club page's links are the only anchors users supply, and they carry `rel="noopener noreferrer nofollow"`; user ids never reach the browser, so staff name people by wallet.

**Reporting activity.** `lib/fillReport.ts` (`mayReport`, `reportTx`) posts a transaction hash to `/api/activity` after a fill or a V2 create, so Momentum counts the deal. It is fire-and-forget, except a fill, which History waits for.

**Not built:** an uploaded banner image (the cover is generated, and the avatar art comes from the assets list), notifications for Club posts and deals, and in-app requests for new Clubs.

## Listing a wallet's Chogs

- **MockChog** implements `ERC721Enumerable`, so the app calls `balanceOf` and then `tokenOfOwnerByIndex(i)` through multicall.
- **Metadata** comes from `tokenURI`. MockChog returns on-chain base64 JSON with an SVG image. `lib/metadata.ts` also handles `ipfs://` and HTTP URIs for when the real collection is plugged in. Metadata is cached forever (`staleTime: Infinity`).
- Concurrent reads (one `tokenURI` per card) are merged into one multicall by the wagmi config's `batch.multicall`.
- **Real Chog:** if it isn't enumerable, fall back to an NFT API or an indexer. Scanning `Transfer` logs isn't practical on the public RPC (see below). Check this first once the real address is known.

## Loading deals without an indexer

The public Monad testnet RPC caps `eth_getLogs` at **100 blocks** per request, so the log scan planned earlier isn't feasible. Deals are read from storage instead ([ADR 0004](adr/0004-read-deals-from-storage.md)):

1. `tradeCount()` → ids `tradeCount … 1`, newest first, `limit` at a time (100 per "Load older" click).
2. One `useReadContracts` multicall of `getTrade(id)` gives terms and live status. `toDeal` drops unknown ids.
3. `tradeCount` is polled every 5s and the batch every 8s, and the previous list is kept while a new batch loads. Every confirmed transaction invalidates all queries.
4. "Expired" is computed from the local clock for lists. The detail page uses the contract's `isExpired`, which is judged against the latest block.

**Known gap:** who filled a *public* deal is only recorded in `TradeFilled`. History shows fills made from this browser (`useLocalFills`) until an indexer exists.

## Transaction flow (`useTxFlow`)

```text
idle ─run─► switching-chain? ─► simulating ─► awaiting-signature ─► pending ─► confirmed
                                     │                 │               │
                                     └────────── error (decoded) ◄─────┘
```

- If the wallet is on another chain, it asks to switch first.
- `simulateContract` surfaces reverts, with the decoded custom error, before the wallet opens.
- `estimateContractGas` + 10% becomes an explicit `gas` limit. Monad charges for the limit, so the buffer is kept small.
- It waits for the receipt, treats `status !== "success"` as an error, then invalidates every react-query query.
- `run()` resolves to the receipt (or null), so callers can parse logs, e.g. `TradeCreated` for the new id.
- `TxButton` shows the stage ("Confirm in wallet…", "Waiting for block…") and `TxStatus` shows the error or the MonadVision link.

## Error messages

`describeError()` in `lib/errors.ts` walks the viem error chain and returns `{ kind, title, message, details }`. It checks, in order: pool rejection, wallet rejection (4001) → "Request cancelled" (shown as a notice, not a failure), contract revert → copy below, insufficient funds, network/RPC failure, wallet problems (no wallet, failed network switch), and otherwise viem's `shortMessage`. `details` holds the raw cause and only appears behind a "Details" toggle. `errorMessage()` is the one-sentence shortcut.

Where errors show up:

- **Transactions and signatures** (`useTxFlow`, `useSignFlow`): a **toast** at the top of the screen, so a failure is seen wherever the page is scrolled, plus an inline `Alert` beside the button via `TxStatus` as the record.
- **Failed loads** (deals, history, deal and intent pages): `LoadError`, a panel with a Try again button that refetches. A deal page shows "does not exist" only for a contract revert; network failures get the panel instead.
- **Wallet connect and network switch**: toasts from `ConnectButton`.
- **A page that crashes while rendering**: `app/error.tsx` keeps the header and wallet up; `app/global-error.tsx` covers the root layout. Both use the `retry` prop of this Next version (not `reset`).

## Create wizard

The header has no Create tab, but a Create button sits beside the wallet. `/create` is also reached from the Create buttons on Home, Deals, History and the Guide, and is one flow with three steps. The stepper only lets you go back; each step has to pass its own checks to Continue, and going back keeps what you typed.

1. **Deal type, and what you want.** Open offer (a note, no ask), request exact assets, or request by trait. The fields below the choice depend on it: a note, an asset list, or a trait picker.
2. **Your assets.** What you give, plus the optional "only this wallet" address and the expiry (1h / 24h / 7d / never, default 24h).
3. **Confirm.** Both sides, the terms, then the approval and Create buttons.

The wizard picks a contract per kind. With `OnDealV2` configured, all three kinds use it; without it, exact and trait requests fall back to the Chog contract ([ADR 0006](adr/0006-trait-requests-in-v2.md)):

| Kind | Contract | Assets | Component |
|---|---|---|---|
| Open offer | `OnDealV2` | any | `MultiFlow` |
| Exact request | `OnDealV2`, or the Chog contract when V2 isn't configured | any, or Chogs + MON | `MultiFlow` / `ChogsFlow` |
| By trait | `OnDealV2`, or the Chog contract when V2 isn't configured | any collection with readable traits (+ optional exact assets), or Chogs + MON | `MultiFlow` / `ChogsFlow` |

### Protocol fee in the app

[ADR 0015](adr/0015-protocol-fee.md). The fee is read from the contracts, never from config (`hooks/useProtocolFee.ts`: `useEscrowFee()` reads `OnDealV2.FEE()`, `useIntentFee()` reads `OnDealIntents.FEE_TOKEN()` and `FEE_AMOUNT()`), and the buttons that need it stay off until it is known. It shows as a "Protocol fee" line (`components/FeeNote.tsx`, hidden when the fee is 0) wherever it is paid, saying it is only charged if the deal completes:

- **Locked deals** (`MultiFlow` review step, `app/v2/deal/[id]` for a taker and for the maker, `ProposalForm`): the create, fill and propose calls send `native amount + fee` as `value`. The deal page also checks for a native `claimable` credit even when the deal has no MON, because a refused fee refund is credited as MON.
- **Signed swaps** (`SignedFlow` review step, `/intent/[hash]`): `useSignFlow.post` reads the fee from the contract at the moment of signing and puts `feeToken` and `fee` into the signed `Intent` (EIP-712 domain version `2`, `lib/intents.ts`). `useIntentReadiness` counts the fee on top of any give of the same token, and adds a "Wrap X MON into WMON" step (the token's `deposit()`) before the approval when the wallet holds enough MON but too little WMON.

Pool rejections `wrong_fee`, `fee_balance` and `fee_allowance` and the stale reasons of the same names have their own copy (`lib/pool.ts`, `lib/intents.ts`).

### Trait requests on V2

`components/create/TraitRequests.tsx` (used by `MultiFlow`, kind `trait`). The maker pastes a collection address (or taps Chog). `hooks/useCollectionTraits.ts` polls `/api/collection-traits`, which scans the collection once on the server (`lib/server/collectionScan.ts`); while it runs the row shows progress, and if the collection can't be read (not an ERC-721, no `totalSupply`, no metadata, over 10,000 tokens) it says why and the request can't continue. When it's ready, traits are grouped by type; the maker picks up to 5 values, and with two or more chooses **any one of them** (OR) or **all of them** (AND), and how many NFTs the taker must send. The count that matches today is shown live. Several trait requests, and ordinary assets ("Also request"), can sit on one deal (10 in all).

`lib/traitSpec.ts` holds the pure logic (matching, spec encoding, validation), `lib/traitDraft.ts` the form state. The Merkle root, ids and proofs are always derived from the scan, never typed. The create call is `createTraitTrade(..., spec)`, with the spec JSON stored on-chain.

On the deal page (`app/v2/deal/[id]`), `hooks/useTraitFill.ts` rebuilds each set from the published spec and only offers a fill when its root equals the deal's ("Checked" / "doesn't match" under each request). `components/TraitFillPanel.tsx` lists the taker's NFTs that match (`hooks/useOwnedInSet.ts`: their token list if the collection is enumerable, otherwise `ownerOf` over the set), they choose the required number, and `fillTraitTrade` is called with the proofs. A deal with no readable spec can't be accepted from the app.

Files: `app/create/page.tsx` (stepper, kind picker, shared `Terms`), `components/create/` (`Stepper`, `KindPicker`, `MultiFlow`, `ChogsFlow`, `TraitPicker`, `parts`), `lib/createFlow.ts` (kinds, expiries, taker check). Each flow owns its own drafts and renders all three steps.

Rules on the Chog-contract side (client-side):

- At least one Chog or some MON on each side, and MON on only one side.
- Up to 10 Chogs per side, no duplicates, and nothing on both sides.
- Offered Chogs are picked from the wallet. Requested Chogs are added by id; `ownerOf` blocks ids that don't exist.
- A private taker must currently own every requested Chog.
- "Who can accept" also takes an X or Discord handle when Privy is on: **Find** calls `/api/profiles/lookup` and lists the wallets that trader shares under it; picking one fills in the address. A handle left unresolved blocks the step. The review shows the taker with `<Who>` ([ADR 0017](adr/0017-deal-by-handle.md)).
- A trait request needs a trait that matches at least one Chog.
- The approval step only appears when a Chog is offered (a MON-only offer needs none).
- On confirm, read the new id from the receipt's `TradeCreated` / `TraitTradeCreated` log and go to `/deal/<id>`.

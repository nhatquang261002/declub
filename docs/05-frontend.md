# 05 · Frontend

Stack: **Next.js 16 (App Router, Turbopack) · React 19 · TypeScript · wagmi 3 · viem 2 · Tailwind 4 · @tanstack/react-query 5**. Package manager: npm.
Writes and most reads go straight to Monad over RPC. The server answers what the chain can't: saves, profiles and Clubs, and the deal book, which searches and filters every deal ([ADR 0020](adr/0020-server-side-deal-book.md)). The app uses `DeClubEscrow` for locked deals and `DeClubIntents` for signed swaps.

Status: Current frontend reference. Implementation status and remaining live verification are
tracked in [06 · Roadmap](06-roadmap.md).

### Config

- `next.config.ts` loads the **repo-root `.env`**, so the web app and the Foundry scripts share one file, but it copies only the `NEXT_PUBLIC_*` values from it. Server secrets (`PRIVY_APP_SECRET`, `UPSTASH_*`, `CRON_SECRET`, …) go in `web/.env.local` or the host's environment. `web/.env*` and real environment variables win over the root file.
- Most values default to the testnet deployment, so `npm run dev` works with no `.env` at all. `NEXT_PUBLIC_DECLUB_ESCROW_ADDRESS` and `NEXT_PUBLIC_DECLUB_INTENTS_ADDRESS` have no default: without them there are no live deals or signed swaps.
- With `NEXT_PUBLIC_PRIVY_APP_ID` set, **Sign in** opens Privy (Google, X, Discord or a wallet), and `/settings` manages linked accounts and active wallets ([ADR 0010](adr/0010-privy-sign-in.md)); a wallet's public profile is `/profile/<address>` ([ADR 0042](adr/0042-profile-page.md)). Email is linkable from `/settings` for recovery but is not currently a login method. Embedded wallets are **off by default**; set `NEXT_PUBLIC_PRIVY_EMBEDDED_WALLETS=true` only after enabling them in the Privy dashboard. Without the app id, only injected wallets (MetaMask, Rabby, Phantom, Backpack and anything else announcing via EIP-6963) are available. WalletConnect is not configured.

### Design tokens

The UI follows a two-layer token architecture: Chog brand primitives live as `--chog-*`
variables, while components consume semantic roles such as `--surface-raised`,
`--content-primary`, `--action-primary`, and `--feedback-warning`. Border radii and shadows
are also centralized as component-ready tokens. This keeps the brand palette changeable without
scattering hex values through JSX or utility definitions.

### ABIs

`@wagmi/cli` with the Foundry plugin reads `contracts/out/{DeClubEscrow,DeClubIntents,MockChog}.sol` and writes `lib/abi.ts` (`deClubEscrowAbi`, `deClubIntentsAbi`, `mockChogAbi`, all `as const`). It isn't generating hooks. The generic wagmi hooks are fully typed from the `as const` ABIs, which is enough. The file is committed so the app builds without Foundry; run `npm run abi` after changing a contract.

### Copy vocabulary

The app isn't limited to Chogs (DeClubEscrow handles any ERC-721, ERC-20 and MON), so UI text says **asset** for anything in a deal, **NFT** only where it must mean an ERC-721, and **MON** for the native coin. "Chog" appears only where it is the actual thing on screen: Chog artwork, the Chog shortcut in the trait picker, and example text. Error copy in `lib/errors.ts` follows the same rule.

### Open Deals search

On the server, over every deal and every signed swap the pool lists ([ADR 0020](adr/0020-server-side-deal-book.md)). The page sends its tab, search, filters and page to `GET /api/deals` (the search a quarter second after typing stops) and shows the page that comes back; the tab counts and the page count are the server's. A bare number matches the deal id or an NFT id on either side; other text matches the maker / taker address, a token address, or a token's on-chain symbol (`lib/dealFilters.ts`). It doesn't look inside trait requests: their traits are in the deal's spec, which only the deal page reads.

### Open Deals tabs

- **Open**: status Open, not expired, and either public or addressed to me.
- **For you**: open direct offers where `taker = me`.
- **All**: every deal and signed swap, any status.

### Open Deals controls

- **Search** box (`DealFilterBar` in `components/DealListControls.tsx`).
- **MON:** Any MON / Offers MON / Wants MON / No MON.
- **Type** (only when signed swaps are on): All types / Locked / Signed.
- **Sort:** Newest first / Ending soon.
- **Pages** of 4 (`components/Pagination.tsx`): numbered buttons, previous / next, and a "Page [n] of N" field. Type a number and press Enter (or leave the field) to jump; out-of-range numbers clamp to the first or last page, Escape cancels. Changing a tab or filter goes back to page 1.

### Notifications

A bell in the header (connected wallets only). There is no event stream to subscribe to ([ADR 0003](adr/0003-no-indexer-in-v1.md)), so `lib/notifications.ts` derives every notification from the newest deals `useDeals` loads (up to 200, polled every 8s) and the wallet's signed swaps:

| Kind | When |
|---|---|
| For you | an open direct offer with `taker = me` |
| Accepted | a deal I made is Filled |
| Ending soon | my open deal expires within 1h |
| Expired | my open deal ran out and its escrow is still locked |

Read state is kept in localStorage per wallet as a resilient browser copy and, when Privy plus a store are configured, is merged with the user's server-side state through `/api/state`. Recent collections use the same per-user server state. On the first visit for a wallet, existing Accepted items are marked read so old deals don't show up as news. Direct offers and expiries stay unread because they need action. The optional browser alert (`Notification` API, turned on from the bell's panel) fires for items that turn up while the tab is in the background. It cannot reach a closed tab; that needs a server-side trigger.

Choices worth knowing:

- **Approvals are exact for tokens, collection-wide for NFTs.** An ERC-20 is approved for the amount in the deal, no more. An NFT collection uses `setApprovalForAll`, the only way to cover several ids in one transaction. The button shows the next missing approval ("1 of 3"), then turns into Create / Accept.
- **Token names come from the token.** The editor shows the symbol and decimals read on-chain under each address, and amounts are parsed with those decimals. A row with more decimals than the token has is rejected instead of rounded.
- **Held payouts:** the deal page reads `claimable` for every asset in the deal and offers a Claim button for what the connected wallet is owed.
- **Lists:** `/deals` renders `Deals`, a page at a time from `/api/deals`. History reads `useDeals` and the wallet's signed swaps.
- **Deal cards:** `DealCard` uses `DealCardFrame` (the chrome signed-swap cards also use) and fills the two sides with `AssetSide`: Chog art for the Chog collection, a plain tile for any other NFT, a token tile with the on-chain symbol, and the MON pill.
- **Search:** see *Open Deals search*: on the server, over the whole book.
- **Fills are per contract:** `useFills(account, contract)` and `useLocalFills` key the record by swap contract, so a redeploy's deal #3 doesn't collide with the old one's. With the server store on, the fill's receipt is what records it (`reportTx` from `useTxFlow`) and the fill watcher catches the rest; without it, the detail page records the fill in this browser after Accept confirms.
- **Open offers ([ADR 0007](adr/0007-open-offers.md)):** a deal with an empty ask (`isOpenOffer`). The card's "wants" side reads *Open to offers*. On the detail page the right-hand panel shows the maker's note as plain text (never linked or rendered as markup) with a "not verified" line, and below the actions come the offers, newest first. The maker sees **Accept & swap** and **Reject** on each active one; whoever made an offer sees **Withdraw my offer** while it is active, even after the deal settled or was cancelled. Anyone else who is allowed to (not the maker, and the private-offer wallet if one is set) gets the **Send offer** form: an `AssetEditor` whose assets are locked in escrow, with the same one-at-a-time approvals. Closed offers sit in a collapsed list. The Accept button and the direct `fillTrade` path are never shown together: `canFill` is false for an open offer.
- **Offers and History:** a wallet whose offer was accepted is the taker. `acceptProposal` emits `TradeFilled` with the proposer as taker, so with the server store on the maker's accept (or the fill watcher) records it for the proposer. Without the store, the detail page records it in this browser (`useLocalFills`) when it sees an accepted offer from the connected wallet, so History picks it up after that visit.
- **Held payouts on open offers:** `claimable` is read for the deal's assets, the accepted offer's assets, and the connected wallet's own offers, not for every offer on the deal.
- **Not built yet:** a "you got an offer" alert in the notifications bell, offer counts on the list cards, and the offer note in list search.

### Choosing NFTs (NFT picker)

An NFT row is no longer a collection address plus a typed id. **+ NFT** (and **Change** on a row) opens `components/NftPicker.tsx`:

1. **Collection.** A search box (`components/AssetSearch.tsx`, over `GET /api/search`, [ADR 0027](adr/0027-on-chain-asset-search.md)): the wallet's holdings first, then verified collections, then the rest. Where the wallet is giving, it starts on **My holdings** with an **All** switch. Beside the server's results it shows the collections the app already knows without an indexer: the Chog collection and `NEXT_PUBLIC_KNOWN_COLLECTIONS` (*Featured*), the ones this browser used before (*Recent*, localStorage), and the ones open deals and signed swaps use (*In open deals*, from `useMarketCollections`). Search matches name, symbol or address. **Pasting a contract address** reads it on-chain first (`supportsInterface` for ERC-721, then name, symbol, supply) and refuses anything that isn't an NFT collection.
2. **Tokens.** On the side the wallet is giving (the editor gets `owner`), the wallet's own NFTs in a grid with art, via `tokenOfOwnerByIndex` (first 100). On the side it is asking for, the collection is browsed a page at a time via `tokenByIndex`, with the holder under each token. Tick several and add them in one go.
3. **Typed id.** Below the grid, for collections that can't list tokens or ids the grid doesn't show. The id is checked with `ownerOf`: it must exist, and on the giving side must be the wallet's.

|---|---|
| `lib/collections.ts` | The read ABI, featured and recent collections, `safeImage` |
| `hooks/useCollection.ts` | `useCollectionInfos`, `useOwnedTokenIds`, `useBrowseTokenIds`, `useTokenViews` (art and name from `tokenURI`), `useTokenOwner` |
| `hooks/useMarketCollections.ts` | Collections used by open deals and signed swaps, most used first |

Choices worth knowing:

- **Holdings come from a provider where one covers the chain.** With `MORALIS_API_KEY` on Monad mainnet, "everything I own" is the wallet's collections and tokens, and tokens are searched by name. On testnet, or if the provider fails, only the assets the app knows are checked (`balanceOf`). A collection Moralis can't find by name (unheld, unverified, not featured, recent or in a deal) is still found by pasting its address. A collection that isn't enumerable still can't list a wallet's tokens, so the picker falls back to the typed, checked id.
- **Names are the contract's own words.** Any contract can call itself "Chog", so every collection is shown with its short address, and only the configured ones are tagged *Featured*.
- **Token art is an image URL from metadata**, so only `http(s)` and inline `data:image/` are shown (`safeImage`), in a plain `<img>` with no referrer.
- Draft rows are unchanged (`token`, `value`), so `assetDraft`, approvals and the contracts see nothing new. ERC-20 rows have the same search: **Search** beside the address field opens `components/TokenPicker.tsx` (holdings first, a pasted address read from its contract), and the address field still works.

### Intents in the frontend (Phase 4)

Signed intents ([ADR 0008](adr/0008-trade-intents.md), [0009](adr/0009-ring-swaps.md)) are optional: the screens appear once `NEXT_PUBLIC_DECLUB_INTENTS_ADDRESS` is set, and `swapIntents` in `lib/contracts.ts` is `undefined` before that. They are not a separate product in the UI: a signed swap is a **deal that settles differently**, so it shares the Create wizard, the deals list and History with locked deals. They read and write the matcher's pool over HTTP (`NEXT_PUBLIC_POOL_URL`, default `http://127.0.0.1:8787`), so the matcher has to be running ([matcher/README.md](../matcher/README.md)). A pool that is down only costs the signed swaps (a notice in the list, an error on the sign step); locked deals read straight from the chain.

| `/create` | Step 1 opens with **How should it settle?**: *Lock assets now* (the three deal kinds, as before) or *Sign only*. Sign only runs `SignedFlow`: want (no MON), give plus a deadline (default 1 hour), then review, the consent notice, **approve** and **Sign and post**. Both steps link back to *Lock assets* for a deal that needs MON or a trait request |
| `/deals` | Locked deals and signed swaps in one grid, each tagged **Locked** or **Signed**. A *Type* filter (All types / Locked / Signed) sits beside the MON and sort filters. Search, MON and sort apply to both |
| `/history` | The wallet's signed swaps in every status beside its locked deals, with the same All / Active / Completed / Expired filter |
| `/guide/deals#settlement` | *Locked deals vs signed swaps*: two cards with one anchored entry per chip, a folded side-by-side table (`#cant-fail`, `#costs-gas`, `#assets-locked`, `#free`, `#nothing-locked`, `#can-fail`), plus three FAQ entries. Shown only when intents are enabled. The sign review's consent notice links here too |
| `/intent/[hash]` | One signed swap: status and what it means, both sides, and for a settled one the cycle and what the maker received. The maker also gets approve-again (when paused), **Remove from pool** and **Cancel on-chain** |

Choices worth knowing:

- **Approvals are the narrowest that work.** An ERC-20 is approved for exactly the amount given, an NFT with `approve(id)`. A checkbox switches to `setApprovalForAll` per collection for fewer transactions, with the wider permission spelled out. Approving is what lets a signed intent execute later without another confirmation, so the consent notice says it.
- **The deadline is short by default** (10 minutes to 7 days, default 1 hour) because a signature that has left the pool can't be recalled.
- **Nonces** are chosen at signing time: above everything this wallet has posted to the pool (cancelled intents included, since their signatures could still settle), skipping any the contract marks used. Keeping them in one 256-bit word keeps settlement cheap.
- **Two kinds of cancel.** *Remove from pool* is a signed `CancelIntent` message, free, but only this pool forgets it. *Cancel on-chain* sends `invalidateNonces`, costs gas, and is the only way to be certain. The detail page says which is which, and keeps offering *Cancel on-chain* after a removal until the deadline (reading `isNonceUsed` so a swap already cancelled on-chain says so).
- **Paused intents** (the pool's `stale`) show why in plain words and, for the maker, the approval to fix it. The matcher revives it on its next 30s pass.
- **Matched in a ring.** `CycleView` lists each wallet's whole `give` and who got it. A pair reads "Swap", three or four wallets "Ring of N". The maker's detail page also shows what they received, surplus included.
- **Notifications.** The bell also lists the wallet's intents: settled, paused (needs action) and dropped, derived from the pool like the deal ones. Settled and dropped ones from before a wallet's first visit are marked read.
- **Ordering in the merged list:** deals have an id but no timestamp, and a signed swap has a timestamp but no id, so there is no honest "newest" across both. Signed swaps come first; *Ending soon* sorts the two together by expiry or deadline.
- **NFTs are picked, not typed.** The sign flow uses the same `AssetEditor` and `NftPicker` as a locked deal; the give side passes `owner={address}`, so the picker shows the wallet's own NFTs.
- **Not built:** counterparty restriction and trait wants (the contract has neither), per-token info beyond symbol and decimals, and push alerts while no tab is open.

### Deal Detail: layout and which button shows

`app/deal/[id]/page.tsx` builds the page from `components/DealSheet.tsx`, the same pieces the signed-swap page uses:

The dock, first match wins:

```text
Filled / Cancelled                 → "This deal is done" / "This deal was cancelled" (read-only)
Open && expired                    → "This deal ran out of time"
                                     [ Reclaim my assets ] (maker) / [ Return assets to maker ] (anyone else)
                                     both call reclaimExpired; there is no Cancel once expired
Open && me == maker                → "Your deal is live" + [ Cancel deal ]
not connected                      → "Want this? Take the deal" (or "Make an offer") + ConnectButton
```

- **Accept isn't gated on ownership.** `canFill = status open && allowed && address && !openOffer`. If the wallet lacks a requested asset, `simulateContract` catches the revert and the decoded error shows before the wallet opens.
- **Steps** (`DealSteps`): Wallet connected, Choose your NFTs (trait requests only), Approve (or "Approve N assets"), Accept & swap. The approvals are the taker's, from `useAssetApprovals` over the requested side.

- **Offers** (`components/Proposals.tsx`): active offers first, the maker gets **Accept & swap** and **Reject** on each, the proposer **Withdraw my offer**. Closed offers sit in a collapsed "Closed offers (n)", older ones behind "Load older offers".
- **Held payouts:** the panel appears only when `claimable` is above zero for the connected wallet. It explains that a payout was rejected (for example by a token or a contract wallet) and is held until claimed.

## Listing a wallet's NFTs

- Generic, for any ERC-721, in `hooks/useCollection.ts`. For an enumerable collection, `useOwnedTokenIds` calls `balanceOf` and then `tokenOfOwnerByIndex(i)` through multicall, capped at the first 100. A collection that isn't enumerable can't be listed, so the picker falls back to a typed id checked with `ownerOf`.
- **Metadata** comes from `tokenURI` (`useTokenViews`). MockChog returns on-chain base64 JSON with an SVG image; `lib/metadata.ts` also handles `ipfs://` and HTTP URIs. Metadata is cached forever (`staleTime: Infinity`). `hooks/useChogs.ts` keeps only `useChogMetadata`, for the Chog art.
- Concurrent reads (one `tokenURI` per card) are merged into one multicall by the wagmi config's `batch.multicall`.
- Scanning `Transfer` logs isn't practical on the public RPC (see below), so "everything I own" across collections needs an NFT API or an indexer.

## Loading deals without an indexer

The public Monad testnet RPC caps `eth_getLogs` at **100 blocks** per request, so a log scan from the browser isn't feasible. Deals are read from storage instead ([ADR 0004](adr/0004-read-deals-from-storage.md)):

1. **The deal list** (`/deals`, a Club's Market) asks the server's deal book (`/api/deals`, [ADR 0020](adr/0020-server-side-deal-book.md)). The server reads `tradeCount()` and multicalls `getTrade` once for everyone: a filled or cancelled deal is read once and kept, open ones (expired included, until reclaimed) are re-read on each refresh, at most every 5s. It holds the book in memory, so a cold start reads it again. The page polls its page every 8s.
2. **History, notifications and the picker's *In open deals*** still read the newest deals from the chain (`useDeals`: `tradeCount` polled every 5s, then one `getTrade` multicall every 8s, the previous list kept while a new batch loads). `toDeal` drops unknown ids. Every confirmed transaction invalidates all queries.
3. "Expired" is computed from the local clock (`displayStatus` in `lib/deals.ts`, which mirrors the contract's `isExpired`), on lists and on the detail page alike. The contract judges it against the block, so a reclaim or fill right at the boundary can still be refused; the simulation says so before the wallet opens.

**Who filled a public deal** is only recorded in `TradeFilled`. With the server store on, History uses the server's receipt-verified fills (`useFills`): the app reports each fill's transaction, and the fill watcher ([ADR 0019](adr/0019-fill-watcher.md), `GET /api/cron/fills`, needs `CRON_SECRET`; finds transactions with Envio HyperSync when `ENVIO_API_TOKEN` is set, [ADR 0051](adr/0051-hypersync-for-the-fill-watcher.md)) follows the chain for the ones made elsewhere. Without the store, History falls back to fills made from this browser (`useLocalFills`).

## Transaction flow (`useTxFlow`)

```text
idle ─run─► switching-chain? ─► simulating ─► awaiting-signature ─► pending ─► confirmed
                                     │                 │               │
                                     └────────── error (decoded) ◄─────┘
```

- If the wallet is on another chain, it asks to switch first.
- `simulateContract` surfaces reverts, with the decoded custom error, before the wallet opens.
- `estimateContractGas` + 10% becomes an explicit `gas` limit. Monad charges for the limit, so the buffer is kept small.
- It waits for the receipt, treats `status !== "success"` as an error, then invalidates every react-query query.
- `run()` resolves to the receipt (or null), so callers can parse logs, e.g. `TradeCreated` for the new id.
- `TxButton` shows the stage ("Confirm in wallet…", "Waiting for block…") and `TxStatus` shows the error or the MonadVision link.

## Error messages

`describeError()` in `lib/errors.ts` walks the viem error chain and returns `{ kind, title, message, details }`. It checks, in order: pool rejection, wallet rejection (4001) → "Request cancelled" (shown as a notice, not a failure), contract revert → copy below, insufficient funds, network/RPC failure, wallet problems (no wallet, failed network switch), and otherwise viem's `shortMessage`. `details` holds the raw cause and only appears behind a "Details" toggle. `errorMessage()` is the one-sentence shortcut.

Where errors show up:

- **Transactions and signatures** (`useTxFlow`, `useSignFlow`): a **toast** at the top of the screen, so a failure is seen wherever the page is scrolled, plus an inline `Alert` beside the button via `TxStatus` as the record.

- **A page that crashes while rendering**: `app/error.tsx` keeps the header and wallet up; `app/global-error.tsx` covers the root layout. Both use the `retry` prop of this Next version (not `reset`).

## Create wizard

The header has no Create tab, but a Create button sits beside the wallet. `/create` is also reached from the Create buttons on Home, Deals, History and the Guide, and is one flow with three steps. ### Protocol fee in the app

[ADR 0015](adr/0015-protocol-fee.md), [ADR 0018](adr/0018-adjustable-protocol-fee.md), [ADR 0033](adr/0033-fee-per-nft.md). The fee is per NFT: `feeUnits(assets)` in `lib/assets.ts` (an NFT is 1, a trait request counts its amount, at least 1) mirrors the contract's, and `sideFee(fee, assets)` is what a side sends. `FeeNote` takes the per-NFT `amount` and the `units`, shows the total and, for more than one NFT, "X for each of your N NFTs". The fee is read from the contracts, never from config. The fee admin can change it, so it is re-read every minute rather than cached for good (`hooks/useProtocolFee.ts`: `useEscrowFee()` reads `DeClubEscrow.fee()`, `useIntentFee()` reads `DeClubIntents.FEE_TOKEN()` and `fee()`, and both read `pendingFee()` / `pendingFeeAt()` for a queued raise). The buttons that need it stay off until it is known. It shows as a "Protocol fee" line (`components/FeeNote.tsx`, hidden when the fee is 0 and no raise is queued) wherever it is paid, saying it is only charged if the deal completes. On the create and signing steps a queued raise adds "Scheduled to rise to X from <date>" and what that means for what is being made.

- **Locked deals** (`MultiFlow` review step, `app/deal/[id]` for a taker and for the maker, `ProposalForm`): create sends `native amount + fee() × the NFTs offered`. A fill or a proposal sends `native amount + deal.fee × the NFTs it hands over`, the fee the deal was listed with (`getTrade(id).fee`, `Deal.fee`), never the current one. The deal page also checks for a native `claimable` credit when the deal has a fee, because a refused fee refund is credited as MON.
- **Signed swaps** (`SignedFlow` review step, `/intent/[hash]`): `useSignFlow.post` reads `fee()` at the moment of signing and signs it as `maxFee` (per NFT given), with `feeToken`, in the `Intent` (EIP-712 domain version `1`, `lib/intents.ts`; `test/intents.test.ts` pins the hashing to the contract's type string). The intent page shows the fee charged now when a cut has brought it below `maxFee`. `useIntentReadiness` counts the fee times the NFTs given on top of any give of the same token, and adds a "Wrap X MON into WMON" step (the token's `deposit()`) before the approval when the wallet holds enough MON but too little WMON.

Pool rejections `wrong_fee`, `fee_balance` and `fee_allowance` and the stale reasons of the same names have their own copy (`lib/pool.ts`, `lib/intents.ts`).

### Trait requests

`components/create/TraitRequests.tsx` (used by `MultiFlow`, kind `trait`). The maker pastes a collection address (or taps Chog). `hooks/useCollectionTraits.ts` polls `/api/collection-traits`, which scans the collection once on the server (`lib/server/collectionScan.ts`); while it runs the row shows progress, and if the collection can't be read (not an ERC-721, no `totalSupply`, no metadata, over 10,000 tokens) it says why and the request can't continue. When it's ready, traits are grouped by type; the maker picks up to 5 values, and with two or more chooses **any one of them** (OR) or **all of them** (AND), and how many NFTs the taker must send. The count that matches today is shown live. Several trait requests, and ordinary assets ("Also request"), can sit on one deal (10 in all).

`lib/traitSpec.ts` holds the pure logic (matching, spec encoding, validation), `lib/traitDraft.ts` the form state. The Merkle root, ids and proofs are always derived from the scan, never typed. The create call is `createTraitTrade(..., spec)`, with the spec JSON stored on-chain.

On the deal page (`app/deal/[id]`), `hooks/useTraitFill.ts` rebuilds each set from the published spec and only offers a fill when its root equals the deal's ("Checked" / "doesn't match" under each request). `components/TraitFillPanel.tsx` lists the taker's NFTs that match (`hooks/useOwnedInSet.ts`: their token list if the collection is enumerable, otherwise `ownerOf` over the set), they choose the required number, and `fillTraitTrade` is called with the proofs. A deal with no readable spec can't be accepted from the app.

Files: `app/create/page.tsx` (stepper, kind picker, shared `Terms`), `components/create/` (`Stepper`, `KindPicker`, `MultiFlow`, `SignedFlow`, `TraitRequests`, `parts`), `lib/createFlow.ts` (kinds, expiries, taker check). Each flow owns its own drafts and renders all three steps.

Rules enforced by the asset editor (client-side):

- At least one asset on each side, and MON on only one side.
- Up to 10 assets per side, at most 5 of them NFTs (`MAX_NFTS_PER_SIDE`; the NFT picker stops at the fifth, and a trait request counts the NFTs it asks for), no duplicate assets, and no asset on both sides.
- NFTs come from `NftPicker`, for any collection. Offered ones are picked from the wallet; requested ones are browsed or typed, and `ownerOf` blocks ids that don't exist.
- The "only this wallet" field (**Only this wallet can accept**, or **Only this wallet can send offers** on an open offer) must be empty or a valid address that isn't your own (`takerError` in `lib/createFlow.ts`). Nothing checks what the taker holds.
- That field also takes an X or Discord handle when Privy is on: **Find** calls `/api/profiles/lookup` and lists the wallets that trader shares under it; picking one fills in the address.
